# 用户自定义智能体设计方案

## 一、现状与问题分析

### 1.1 当前架构概览

| 模块 | 职责 | 接口路径 | 核心实体 |
|------|------|----------|----------|
| **Application** | 应用管理（CRUD、配置、分享、统计） | `/api/v1/applications` | Application + ApplicationConfig |
| **Session/Chat** | 会话与消息 | `/api/v1/chat/sessions` | Session(appId) + Message |
| **Agent** (agentx) | 智能体运行时 | 示例: `/api/v1/agents` | AgentDefinition + AgentRegistry |

### 1.2 核心矛盾

1. **概念割裂**：用户创建的是「应用」，但智能体能力在 agentx 的 `AgentRegistry` 中，以 `agentId` 为键，二者无直接关联。
2. **配置双轨**：`ApplicationConfig`（模型、知识库、提示词、工作流）与 `AgentDefinition`（model、knowledgeBaseIds、systemPrompt、workflowId）结构相似但字段不统一，难以复用。
3. **入口别扭**：若通过「应用入口」提供智能体服务，需要：Session(appId) → 查 Application → 转 AgentDefinition → 注册/获取 Agent → 调用 `AgentRegistry.chat`，链路冗长且应用与智能体职责混淆。
4. **Agent 无持久化**：`AgentRegistry` 仅内存管理，Agent 定义来自 YAML/JSON 或代码注册，用户无法在平台内创建、编辑、版本化管理智能体。

### 1.3 设计目标

- **智能体作为一等公民**：用户可独立创建、配置、发布、复用智能体。
- **应用与智能体解耦**：应用可「绑定」智能体，也可不绑定（走简单 LLM 流程）。
- **统一配置模型**：智能体配置与现有资源（模型、知识库、工作流、工具）对齐，便于组装。
- **清晰 API 边界**：智能体管理、对话、统计各有专属接口，不依赖应用入口「拐弯」调用。

## 二、概念模型

### 2.1 实体关系

```
┌─────────────────────────────────────────────────────────────────┐
│                    Application (应用)                              │
│  • 用户访问统一入口                                                │
│  • 提供个性化配置（用户偏好、默认智能体等）                          │
└────────┬────────────────────────────────────┬─────────────────────┘
         │ 1:N 绑定                           │ Session.appId
         ▼                                    ▼
┌─────────────────────┐              ┌─────────────────┐
│ ApplicationAgent    │              │    Session      │
│ (应用-智能体绑定)    │              │    (会话)       │
│ • applicationId     │              │ • appId         │
│ • agentId           │              │ • 可选: agentId  │
│ • sortOrder         │              │   (用户选择的)    │
│ • isDefault         │              └────────┬────────┘
└────────┬────────────┘                       │
         │                                    │ 解析 agentId
         ▼                                    ▼
┌─────────────────┐                   ┌─────────────────┐
│     Agent       │◄──────────────────│ AgentRegistry    │
│   (智能体)       │  .chat(agentId,   │ .chat(agentId,   │
└─────────────────┘   sessionId, msg) │  sessionId, msg) │
                                       └─────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│            UserApplicationConfig (用户应用个性化配置)              │
│  • userId + applicationId → defaultAgentId, 其他偏好               │
└─────────────────────────────────────────────────────────────────┘
```

- **Agent**：用户可创建的智能体实体，持久化存储，配置即 `AgentDefinition` 的持久化形态。
- **Application**：用户访问的**统一入口**，可绑定**多个智能体**；通过 `ApplicationAgent` 关联表管理绑定关系，支持排序与默认智能体。
- **UserApplicationConfig**：用户在某应用下的**个性化配置**，如默认使用的智能体、界面偏好等。
- **Session**：继续使用 `appId`；通过 Application + UserApplicationConfig 解析出 `agentId`（用户可选或使用默认），再调用 `AgentRegistry.chat(agentId, sessionId, message)`。

### 2.2 配置对齐

| AgentDefinition 字段 | 对应业务资源 | 说明 |
|---------------------|--------------|------|
| model.provider + modelName | Model.id（平台模型表） | 用 modelId 替代，从 Model 解析 provider/modelName |
| knowledgeBaseIds | KnowledgeBase.id（Long） | 与 ApplicationConfig.resources 一致 |
| toolIds | Tool 插件 ID（String） | 保持 |
| workflowId | Workflow.id（Long） | 与 ApplicationConfig 一致 |
| skillIds | Skill.name() | 保持 |
| datasetIds | Dataset.id | 可选扩展 |
| openApiIds | ApiCollection.id | 可选扩展 |

## 三、详细接口设计

### 3.1 智能体管理 REST API

**Base Path**: `GET/POST /api/v1/agents`

#### 3.1.1 创建智能体

```
POST /api/v1/agents
Content-Type: application/json
```

**请求体 (AgentCreateDto)**:

```json
{
  "name": "客服助手",
  "description": "处理售前售后咨询的智能客服",
  "interactionMode": "CHATBOT",
  "reasoningStrategy": "FUNCTION_CALLING",
  "autonomyLevel": "ASSISTANT",
  "modelId": 1,
  "systemPrompt": "你是专业的客服助手...",
  "welcomeMessage": "您好，有什么可以帮您？",
  "suggestedQuestions": ["如何退货？", "订单查询"],
  "resources": {
    "knowledgeBaseIds": [1, 2],
    "toolIds": ["search", "query_order"],
    "workflowId": 10,
    "skillIds": ["customer_service"]
  },
  "memory": {
    "strategy": "TOKEN_WINDOW",
    "maxTokens": 8000
  },
  "guardrails": {
    "inputGuardrailIds": ["content_filter"],
    "outputGuardrailIds": []
  },
  "variables": {
    "companyName": "XX科技"
  }
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| name | string | 是 | 智能体名称 |
| description | string | 否 | 描述 |
| interactionMode | enum | 否 | CHATBOT/COMPLETION/WORKFLOW/AGENT_AS_API/MULTI_TURN_TASK，默认 CHATBOT |
| reasoningStrategy | enum | 否 | SIMPLE_LLM/FUNCTION_CALLING/REACT/PLAN_AND_EXECUTE/MULTI_AGENT，默认 FUNCTION_CALLING |
| autonomyLevel | enum | 否 | TOOL/ASSISTANT/COLLABORATOR/DELEGATE/AUTONOMOUS，默认 ASSISTANT |
| modelId | long | 是 | 平台模型 ID，对应 Model 表 |
| systemPrompt | string | 否 | 系统提示词 |
| welcomeMessage | string | 否 | 开场白 |
| suggestedQuestions | string[] | 否 | 建议问题 |
| resources | object | 否 | 关联资源 |
| resources.knowledgeBaseIds | long[] | 否 | 知识库 ID，最多 5 个 |
| resources.toolIds | string[] | 否 | 工具 ID |
| resources.workflowId | long | 否 | 工作流 ID |
| resources.skillIds | string[] | 否 | 技能名称 |
| memory | object | 否 | 记忆策略 |
| guardrails | object | 否 | 护栏配置 |
| variables | map | 否 | 变量注入 |

**响应**: `ApiLocaleResult<AgentDetailVo>`

#### 3.1.2 更新智能体

```
PATCH /api/v1/agents/{id}
Content-Type: application/json
```

**请求体**: 与创建相同结构，仅传需更新字段（部分更新）。

**响应**: `ApiLocaleResult<AgentDetailVo>`

**副作用**: 若智能体已注册到 AgentRegistry，需 `unregister` 后按新配置重新 `register`。

#### 3.1.3 获取智能体详情

```
GET /api/v1/agents/{id}
```

**响应**: `ApiLocaleResult<AgentDetailVo>`

#### 3.1.4 智能体列表（分页）

```
GET /api/v1/agents?page=1&size=10&keyword=xxx&status=ACTIVE
```

**查询参数**:

| 参数 | 类型 | 说明 |
|------|------|------|
| page | int | 页码 |
| size | int | 每页条数 |
| keyword | string | 名称/描述模糊搜索 |
| status | enum | ACTIVE/INACTIVE |
| interactionMode | enum | 筛选交互模式 |

**响应**: `ApiLocaleResult<PageResult<AgentListVo>>`

#### 3.1.5 删除智能体

```
DELETE /api/v1/agents/{id}?force=false
```

- `force=false`：若被应用引用则禁止删除。
- `force=true`：强制删除，解除应用绑定。

#### 3.1.6 发布/下线智能体

```
PUT /api/v1/agents/{id}/status
?status=ACTIVE | INACTIVE
```

- ACTIVE：注册到 AgentRegistry，可被对话。
- INACTIVE：从 AgentRegistry 注销，不可对话。

### 3.2 智能体对话 API

**Base Path**: `POST /api/v1/agents/chat`

#### 3.2.1 同步对话

```
POST /api/v1/agents/chat
Content-Type: application/json
```

**请求体 (AgentChatRequestDto)**:

```json
{
  "agentId": "agent_123",
  "sessionId": "sess_abc",
  "message": "你好，我想查询订单"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| agentId | string | 是 | 智能体 ID（持久化实体的业务 ID，如 "agent_123" 或 数据库主键转 string） |
| sessionId | string | 否 | 会话 ID，用于记忆隔离，默认 "default" |
| message | string | 是 | 用户消息 |

**响应 (AgentChatResponseVo)**:

```json
{
  "code": 0,
  "data": {
    "agentId": "agent_123",
    "sessionId": "sess_abc",
    "reply": "您好，请提供您的订单号...",
    "latencyMs": 1200
  }
}
```

#### 3.2.2 流式对话

```
POST /api/v1/agents/chat/stream
Content-Type: application/json
Accept: text/event-stream
```

**请求体**: 同同步对话。

**响应**: SSE 流，`data:` 行携带增量文本。

---

### 3.3 通过应用入口的对话（兼容现有 Session）

当 Session 关联的 Application 绑定了 `agentId` 时，`MessageFacade.sendMessage` 内部应：

1. 根据 `sessionId` 查 Session → 得 `appId`。
2. 查 Application → 得 `agentId`（若存在）。
3. 若 `agentId` 非空：调用 `AgentRegistry.chat(agentId, sessionId, message)`。
4. 若 `agentId` 为空：走现有 `ChatService.sendMessage`（简单 LLM）。

这样「应用入口」与「智能体入口」统一到同一套对话逻辑，只是入口不同：
- 直接调用 `/api/v1/agents/chat`：显式指定 agentId。
- 通过 `/api/v1/chat/sessions/{sessionId}/messages`：隐式通过 appId → agentId 解析。

### 3.4 应用与智能体绑定

#### 3.4.1 更新应用配置时绑定智能体

在 `ApplicationConfig` 或 `ApplicationUpdateDto` 中新增：

```json
{
  "agentId": "agent_123"
}
```

- `agentId` 为空：不绑定，会话走简单 LLM。
- `agentId` 非空：绑定，会话走 Agent。

#### 3.4.2 获取可绑定的智能体列表

```
GET /api/v1/agents?bindable=true&status=ACTIVE
```

用于应用配置页的「选择智能体」多选/下拉。

#### 3.4.3 用户个性化配置（应用级）

```
GET  /api/v1/applications/{appId}/user-config          # 获取当前用户在该应用下的个性化配置
PUT  /api/v1/applications/{appId}/user-config         # 更新当前用户个性化配置
```

**UserApplicationConfigDto**（更新请求体）:

```json
{
  "defaultAgentId": 2,
  "preferences": {
    "theme": "dark",
    "autoExpandSuggestions": true
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| defaultAgentId | long | 用户在该应用下默认使用的智能体 ID，须为应用已绑定的 agentIds 之一 |
| preferences | map | 其他个性化偏好（主题、UI 行为等），可扩展 |

- 若用户未设置 `defaultAgentId`，则使用应用的 `defaultAgentId`。
- 若应用未设置 `defaultAgentId`，则使用绑定列表中的第一个。

## 四、领域模型与持久化

### 4.1 Agent 实体（数据库）

使用类型化 model 替代 JSON 字符串，便于类型安全与 JPA 映射。

#### 4.1.1 主实体 Agent

```java
@Entity
@Table(name = "ai_agent")
public class Agent {
  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  private String name;
  private String description;
  private String status;  // ACTIVE, INACTIVE

  @Enumerated(EnumType.STRING)
  private InteractionMode interactionMode;
  @Enumerated(EnumType.STRING)
  private ReasoningStrategy reasoningStrategy;
  @Enumerated(EnumType.STRING)
  private AutonomyLevel autonomyLevel;

  private Long modelId;  // 关联 Model
  @Column(columnDefinition = "text")
  private String systemPrompt;
  private String welcomeMessage;

  @ElementCollection
  @CollectionTable(name = "ai_agent_suggested_questions", joinColumns = @JoinColumn(name = "agent_id"))
  @Column(name = "question")
  private List<String> suggestedQuestions;

  // 关联资源
  @ElementCollection
  @CollectionTable(name = "ai_agent_knowledge_base_ids", joinColumns = @JoinColumn(name = "agent_id"))
  @Column(name = "knowledge_base_id")
  private List<Long> knowledgeBaseIds;

  @ElementCollection
  @CollectionTable(name = "ai_agent_tool_ids", joinColumns = @JoinColumn(name = "agent_id"))
  @Column(name = "tool_id")
  private List<String> toolIds;

  private Long workflowId;

  @ElementCollection
  @CollectionTable(name = "ai_agent_skill_ids", joinColumns = @JoinColumn(name = "agent_id"))
  @Column(name = "skill_id")
  private List<String> skillIds;

  @ElementCollection
  @CollectionTable(name = "ai_agent_dataset_ids", joinColumns = @JoinColumn(name = "agent_id"))
  @Column(name = "dataset_id")
  private List<Long> datasetIds;

  @ElementCollection
  @CollectionTable(name = "ai_agent_api_collection_ids", joinColumns = @JoinColumn(name = "agent_id"))
  @Column(name = "api_collection_id")
  private List<Long> apiCollectionIds;

  @Embedded
  @AttributeOverrides({
      @AttributeOverride(name = "strategy", column = @Column(name = "memory_strategy")),
      @AttributeOverride(name = "windowSize", column = @Column(name = "memory_window_size")),
      @AttributeOverride(name = "maxTokens", column = @Column(name = "memory_max_tokens")),
      @AttributeOverride(name = "summaryPrompt", column = @Column(name = "memory_summary_prompt", columnDefinition = "text"))
  })
  private AgentMemoryConfig memory;

  @Embedded
  @AttributeOverrides({
      @AttributeOverride(name = "inputGuardrailIds", column = @Column(name = "input_guardrail_ids")),
      @AttributeOverride(name = "outputGuardrailIds", column = @Column(name = "output_guardrail_ids"))
  })
  private AgentGuardrailsConfig guardrails;

  @ElementCollection
  @CollectionTable(name = "ai_agent_variables", joinColumns = @JoinColumn(name = "agent_id"))
  @MapKeyColumn(name = "var_key")
  @Column(name = "var_value")
  private Map<String, String> variables;

  private String tenantId;
  private LocalDateTime createdDate;
  private LocalDateTime lastModifiedDate;
}
```

#### 4.1.2 嵌入模型 AgentMemoryConfig

```java
@Embeddable
@Data
@NoArgsConstructor
@AllArgsConstructor
public class AgentMemoryConfig {
  @Enumerated(EnumType.STRING)
  private MemoryStrategy strategy;  // NONE, MESSAGE_WINDOW, TOKEN_WINDOW, SUMMARY
  private Integer windowSize;
  private Integer maxTokens;
  @Column(columnDefinition = "text")
  private String summaryPrompt;
}
```

#### 4.1.3 嵌入模型 AgentGuardrailsConfig

```java
@Embeddable
@Data
@NoArgsConstructor
@AllArgsConstructor
public class AgentGuardrailsConfig {
  @ElementCollection
  @CollectionTable(name = "ai_agent_input_guardrail_ids", joinColumns = @JoinColumn(name = "agent_id"))
  @Column(name = "guardrail_id")
  private List<String> inputGuardrailIds;

  @ElementCollection
  @CollectionTable(name = "ai_agent_output_guardrail_ids", joinColumns = @JoinColumn(name = "agent_id"))
  @Column(name = "guardrail_id")
  private List<String> outputGuardrailIds;
}
```

> **说明**：`AgentGuardrailsConfig` 内含 `@ElementCollection`，嵌入时需通过 `@Embedded` 的 `joinColumns` 传递 `agent_id`。若 JPA 实现不支持嵌套，可改为在 `Agent` 上直接定义 `inputGuardrailIds`、`outputGuardrailIds` 两个 `@ElementCollection`，或使用独立表 `ai_agent_guardrails` 存储。

**简化方案**（若嵌套 `@ElementCollection` 有兼容问题）：将 `guardrails` 拆为 Agent 上的两个字段：

```java
@ElementCollection
@CollectionTable(name = "ai_agent_input_guardrail_ids", joinColumns = @JoinColumn(name = "agent_id"))
@Column(name = "guardrail_id")
private List<String> inputGuardrailIds;

@ElementCollection
@CollectionTable(name = "ai_agent_output_guardrail_ids", joinColumns = @JoinColumn(name = "agent_id"))
@Column(name = "guardrail_id")
private List<String> outputGuardrailIds;
```

### 4.2 Agent 与 AgentRegistry 的桥接

- **agentId**：对外使用 `String.valueOf(agent.getId())` 或 `"agent_" + id`，与 AgentRegistry 的 key 一致。
- **发布(ACTIVE)**：`AgentFacade.publish(id)` → 从 DB 加载 Agent → 转为 `AgentDefinition` → `AgentRegistry.register(definition)`。
- **下线(INACTIVE)**：`AgentFacade.unpublish(id)` → `AgentRegistry.unregister(agentId)`。
- **更新配置**：先 `unregister`，再按新配置 `register`。

### 4.3 Application 扩展

在 `Application` 表增加字段：

```sql
ALTER TABLE ai_application ADD COLUMN agent_id BIGINT NULL;
```

或若 Agent 使用字符串 ID，则 `agent_id VARCHAR(64) NULL`。应用配置页可展示「绑定智能体」选择器。

1. Application 表增加 `agentId` 字段。
2. ApplicationConfig/UpdateDto 支持 `agentId`。
3. 修改 `ChatService` 或 `MessageFacade`：Session → Application → agentId → AgentRegistry.chat（若绑定）。

### 6.4 阶段四：前端

1. 新增「智能体」管理页：列表、创建、编辑、发布、删除。

## 6.5 应用与智能体参数删除策略（TODO 待确认）

**问题**：应用和智能体属于一对多关系，原有应用和智能体相关参数是不是可以删除？

**分析**：

| 场景 | 应用绑定 Agent | 应用未绑定 Agent |
|------|----------------|------------------|
| 对话逻辑 | 使用 Agent 的 model、resources、prompts | 使用 Application 的 model、resources、prompts（简单 LLM） |
| 配置来源 | Agent 实体 | ApplicationConfig |

**结论**：

1. **不能完全删除**：当 `agentId` 为空时，会话走「简单 LLM」模式，仍需 Application 的 model、resources、prompts 配置。
2. **可逐步简化**：
   - 当应用绑定 Agent 后，对话时**忽略** Application 的 model/resources/prompts，仅使用 Agent 的配置。
   - AIApplication 表上的冗余字段（modelId、knowledgeBaseIds、workflowId 等）与 ApplicationConfig 重复，可考虑：
     - **选项 A**：保留，用于未绑定 Agent 时的简单 LLM。
     - **选项 B**：迁移后仅从 config JSON 解析，删除冗余列（需评估性能与兼容性）。
3. **TODO 待产品确认**：
   - 是否强制每个应用至少绑定一个 Agent？（若强制，可考虑删除 Application 的智能体相关参数）
   - 一对多（ApplicationAgent 表）与当前单 agentId 的演进路径？

## 七、与现有 agentx-api-examples 的关系

- `agentx-api-examples` 中的 `AgentManagementController`、`AgentChatController` 可作为**参考实现**。
- Angus 核心应实现自己的 `AgentRest`、`AgentChatRest`，与租户、权限、审计等集成，并持久化 Agent 到业务库。
- 最终可考虑将 agentx-api-examples 的 Agent 接口标记为 deprecated，或仅用于开发/演示。

## 八、OpenAI 对话标准接口兼容性分析

### 8.1 结论：可以遵循 OpenAI 标准

基于当前设计，**完全可以提供遵循 OpenAI Chat Completions 标准的接口**，且与 Agent/Application 架构天然契合。项目内已有 `OpenAIChatRest` 占位类，可直接实现。

### 8.2 OpenAI Chat Completions 标准要点

| 项目 | OpenAI 标准 | 说明 |
|------|-------------|------|
| 路径 | `POST /v1/chat/completions` | 可挂载为 `/api/v1/chat/completions` 或 `/v1/chat/completions` |
| 认证 | `Authorization: Bearer <api_key>` | 与现有 API Key / 租户鉴权对齐 |
| 请求体 | `model`, `messages`, `stream`, `temperature`, `max_tokens` 等 | 见下表 |
| 响应 | `id`, `choices`, `usage` | 流式时为 SSE `data:` 行 |

**核心请求参数**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| model | string | 是 | 模型标识，可映射为 Agent ID 或 Model ID |
| messages | array | 是 | `[{role: "system"\|"user"\|"assistant", content: string}]` |
| stream | boolean | 否 | 是否流式返回，默认 false |
| temperature | number | 否 | 0-2 |
| max_tokens | integer | 否 | 最大生成 token 数 |
| ... | | | 其他可选参数 |

### 8.3 与当前设计的映射关系

| OpenAI 参数 | 映射到 Angus 设计 | 说明 |
|-------------|-------------------|------|
| **model** | Agent ID 或 Model ID | 见 8.4 |
| **messages** | 转为 Agent 输入 | system → 合并/覆盖 Agent.systemPrompt；user/assistant → 历史上下文 |
| **stream** | 调用 `AgentRegistry.chatStream` 或 `chat` | 直接支持 |
| **temperature / max_tokens** | 覆盖 Agent 的 ModelConfig | 请求级覆盖，可选 |
| **sessionId** | 非标准，扩展 | 通过 Header 或自定义字段传递，用于服务端记忆 |

### 8.4 model 参数的双模式解析

为兼容不同使用场景，`model` 支持两种解析方式：

| model 值格式 | 解析为 | 行为 |
|--------------|--------|------|
| `agent_{id}` 或纯数字 `123` | Agent ID | 走完整 Agent 流程：工具、RAG、工作流、护栏等 |
| `{provider}-{modelName}` 如 `gpt-4`、`deepseek-chat` | 平台 Model | 走简单 LLM 调用，无工具/RAG |

**推荐约定**：

- `agent_123` 或 `123`（在 Agent 表中存在）→ 使用 Agent
- 否则按 `provider-modelName` 查找 Model，走简单 Chat

### 8.5 messages 与 Agent 的转换规则

```
OpenAI messages:
[
  { "role": "system", "content": "你是一个助手" },   // 可选，与 Agent.systemPrompt 合并
  { "role": "user", "content": "你好" },
  { "role": "assistant", "content": "您好！" },
  { "role": "user", "content": "今天天气怎么样？" }   // 最后一条 user 为当前问题
]

转换逻辑：
1. 提取 role=system 的 content，与 Agent.systemPrompt 合并（请求中的 system 可覆盖或追加）
2. user/assistant 序列作为对话历史
3. 若启用服务端记忆：sessionId 对应 MemoryId，历史可部分依赖服务端存储
4. 若不启用：必须由客户端传全量 messages
```

### 8.6 会话与记忆（sessionId）

OpenAI 标准**无 sessionId**，客户端通常传全量 `messages`。为支持服务端记忆，可采用扩展方式：

| 方式 | 说明 |
|------|------|
| **Header** | `X-Session-Id: sess_xxx` 或 `X-Conversation-Id` |
| **请求体扩展** | 自定义字段 `session_id`（非标准，部分 SDK 支持） |
| **无记忆模式** | 不传 sessionId，仅用本次 messages，不读写服务端记忆 |

推荐：优先支持 `X-Session-Id` Header，与现有 Session 体系一致。

### 8.7 应用入口与 OpenAI 接口的统一

当通过**应用**访问时，可增加「应用级」Chat Completions 端点：

```
POST /api/v1/applications/{appId}/chat/completions
```

- 请求体与 OpenAI 标准一致（含 `model`、`messages`、`stream` 等）。
- `model` 可选：不传时，按应用绑定 + 用户个性化配置解析出默认 Agent。
- 传 `model` 时，需校验该 Agent 属于该应用绑定列表。

这样既符合 OpenAI 标准，又保留「应用作为统一入口」的设计。

### 8.8 接口路径建议

| 路径 | 用途 | 说明 |
|------|------|------|
| `POST /v1/chat/completions` | 通用 OpenAI 兼容 | 必须传 `model`，面向 SDK/第三方集成 |
| `POST /api/v1/chat/completions` | 同上，带 API 前缀 | 与现有 `/api/v1` 风格一致 |
| `POST /api/v1/applications/{appId}/chat/completions` | 应用入口 | `model` 可选，按应用+用户解析默认 Agent |
| `POST /api/v1/agents/{agentId}/chat/completions` | 智能体直连 | 等价于 `model=agent_{agentId}` |

### 8.9 响应格式（兼容 OpenAI）

**同步响应示例**：

```json
{
  "id": "chatcmpl-xxx",
  "object": "chat.completion",
  "created": 1699999999,
  "model": "agent_123",
  "choices": [{
    "index": 0,
    "message": {
      "role": "assistant",
      "content": "您好，有什么可以帮您？"
    },
    "finish_reason": "stop"
  }],
  "usage": {
    "prompt_tokens": 10,
    "completion_tokens": 20,
    "total_tokens": 30
  }
}
```

**流式响应**：SSE，`data:` 行格式与 OpenAI 一致，如 `data: {"choices":[{"delta":{"content":"你"}}]}`，结束为 `data: [DONE]`。

### 8.10 实施要点

1. **实现 `OpenAIChatRest`**：接收 OpenAI 格式请求，解析 `model` → Agent 或 Model，调用 `AgentRegistry.chat`/`chatStream` 或简单 LLM。
2. **Messages 转换器**：`OpenAIMessagesConverter`，将 messages 转为 Agent 所需的 systemPrompt + 历史。
3. **响应组装**：将 Agent/LLM 输出封装为 OpenAI 标准响应结构。
4. **Tool Calls**：若 Agent 使用 function calling，需将 `tool_calls` 格式与 LangChain4j 的 Tool 结果互转（可选，进阶能力）。
