# 工作流编排设计器开发指导

> 本文档面向前端开发者，基于对 AngusAI 工作流编排后端实现的分析，提供完整的工作流设计器实现指南，并补全浏览器端设计器的完整功能设计（含调试、执行可视化等，参考 n8n 等业界流程设计器）。

---

## 一、后端工作流编排实现分析

### 1.1 架构概览

工作流编排分为两层：

| 层次 | 模块 | 职责 |
|------|------|------|
| **业务层** | Angus Core | 工作流 CRUD、持久化、REST API、业务状态管理 |
| **执行层** | AgentX | DSL 解析、校验、DAG 执行引擎、节点执行器 |

二者目前部分未打通：Core 的 `execute` 为占位实现，执行引擎依赖 AgentX 的 `WorkflowEngine` 和 `WorkflowDefinitionProvider`。

### 1.2 数据模型

#### 1.2.1 前端/Core 持久化模型：WorkflowConfig

前端设计器保存的配置与 `WorkflowConfig` 对应：

```java
// WorkflowConfig (Angus Core 持久化)
{
  nodes: [ { id, type, position, data, style } ],
  edges: [ { id, source, target, sourceHandle, targetHandle, type, animated, label, style } ],
  variables: [ { name, type, defaultValue, required, description } ],
  triggers: [ { type, config } ],
  execution: { mode, timeout, parallel, maxConcurrency },
  errorHandling: { strategy, maxRetries, retryableErrors, fallbackActions },
  logging: { enabled, level, loggers, retention },
  notification: { enabled, channels, templates },
  // ... 其他配置
}
```

**节点 (WorkflowNode)**：`id`, `type`, `position`, `data`, `style`  
**边 (WorkflowEdge)**：`id`, `source`, `target`, `sourceHandle`, `targetHandle`, `type`, `animated`, `label`, `style`

#### 1.2.2 AgentX 执行层模型：WorkflowDefinition / NodeDefinition

执行引擎使用链式/配置式连接，而非显式 edges：

```java
// NodeDefinition (AgentX 执行)
{
  id, type, config, outputs,
  next: "下一节点ID",           // 线性链
  config.ifTrue / config.ifFalse,  // CONDITION 分支
  config.branches: ["id1","id2"],   // PARALLEL 分支
  retry, timeout, onFailure, onTimeout
}
```

### 1.3 配置转换（前后端打通关键）

| 方向 | 说明 | 当前状态 |
|------|------|----------|
| **前端 → AgentX** | WorkflowConfig (nodes+edges) → WorkflowDefinition (nodes+next) | ❌ 未实现 |
| **AgentX → 前端** | WorkflowDefinition → WorkflowConfig | ❌ 未实现 |
| **保存配置** | WorkflowAssembler.toConfig() 未将 dto.nodes/edges 写入 WorkflowConfig | ⚠️ TODO |

**转换规则概要：**

- **线性链**：`edge.source → edge.target` 转为 `sourceNode.next = targetNode.id`
- **CONDITION**：两条边 `(source, ifTrueTarget)` 与 `(source, ifFalseTarget)` 转为 `config.ifTrue` / `config.ifFalse`
- **PARALLEL**：多条边从同一 source 出发到多个 target，转为 `config.branches = [target1, target2, ...]`
- **SWITCH**：按 `label` 或 `targetHandle` 映射到 `config.cases` 和 `config.default`

### 1.4 节点类型与执行器

| 节点类型 | 说明 | 连接方式 | 执行器 |
|----------|------|----------|--------|
| START | 入口 | 单出边 | StartNodeExecutor |
| END | 终止 | 无出边 | EndNodeExecutor |
| LLM | 大模型调用 | 单出边 | LlmNodeExecutor |
| AGENT | Agent 调用 | 单出边 | AgentNodeExecutor |
| TOOL | 工具调用 | 单出边 | ToolNodeExecutor |
| HTTP | HTTP 请求 | 单出边 | HttpNodeExecutor |
| CODE | 代码片段 | 单出边 | CodeNodeExecutor |
| CONDITION | 条件分支 | ifTrue/ifFalse | ConditionNodeExecutor |
| SWITCH | 多路分支 | cases/default | SwitchNodeExecutor |
| LOOP | for-each | body/next | LoopNodeExecutor |
| WHILE | 条件循环 | body/next | WhileNodeExecutor |
| PARALLEL | 并行 | branches | ParallelNodeExecutor |
| WAIT | 等待(人工/延时) | 单出边 | WaitNodeExecutor |
| SUB_WORKFLOW | 子工作流 | 单出边 | SubWorkflowNodeExecutor |
| SET_VARIABLE | 设置变量 | 单出边 | SetVariableNodeExecutor |
| KNOWLEDGE_RETRIEVAL | 知识库检索 | 单出边 | KnowledgeRetrievalNodeExecutor |

节点规范（参数说明）详见 `WorkflowSpecRegistry` / `NodeTypeSpec`。

### 1.5 执行引擎流程

1. 合并输入变量与工作流级 `variables`
2. 拓扑排序（START → next / ifTrue|ifFalse / branches）
3. 按序执行各节点，调用对应 `NodeExecutor.execute()`
4. 根据全局 `FailurePolicy`（STOP/CONTINUE/ROLLBACK）处理异常
5. 输出 `WorkflowExecutionResult`：`executionId`、`status`、`output`、`nodeRecords`

### 1.6 REST API

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/workflows` | 创建工作流 |
| PATCH | `/api/v1/workflows/{id}` | 更新基本信息 |
| PUT | `/api/v1/workflows/{id}/config` | 更新 nodes/edges 配置 |
| POST | `/api/v1/workflows/{id}/execute` | 执行（调试/手动） |
| POST | `/api/v1/workflows/{id}/start` | 启动 |
| POST | `/api/v1/workflows/{id}/stop` | 停止 |
| GET | `/api/v1/workflows/{id}` | 详情 |
| GET | `/api/v1/workflows` | 列表 |
| GET | `/api/v1/workflows/stats` | 统计 |
| GET | `/api/v1/workflows/execution-logs` | 执行日志 |
| GET | `/api/v1/workflows/executions/{executionId}` | 执行详情 |

## 二、前端实现指导

### 2.1 技术栈与依赖

- **ReactFlow**：画布、节点、边、Controls、MiniMap、Background
- 现有结构：`WorkflowEditor.tsx`、`useWorkflowEditor.ts`、`WorkflowDesignPage.tsx`

### 2.2 核心组件职责

| 组件 | 职责 |
|------|------|
| `WorkflowEditor` | 画布、 toolbar、节点/边渲染、保存/启动/全屏 |
| `useWorkflowEditor` | 加载配置、nodes/edges 状态、connect、保存、启动/停止 |
| `WorkflowDesignPage` | 设计页容器、标题、返回 |

### 2.3 节点与边的数据结构（前端）

与 `WorkflowConfig` 保持兼容：

```typescript
interface WorkflowNode {
  id: string;
  type: string; // input | output | 业务节点类型
  position: { x: number; y: number };
  data: { label: string; config?: Record<string, unknown> };
  style?: Record<string, string | number>;
}

interface WorkflowEdge {
  id: string;
  source: string;
  target: string;
  sourceHandle?: string;
  targetHandle?: string;
  type?: string;
  animated?: boolean;
  label?: string;
  data?: Record<string, unknown>;
}
```

### 2.4 节点类型映射与 palette

建议建立节点面板（palette），按 `NodeType` 分类：

- **流程控制**：START, END, CONDITION, SWITCH, LOOP, WHILE, PARALLEL, WAIT
- **AI/智能**：LLM, AGENT, KNOWLEDGE_RETRIEVAL
- **集成**：HTTP, TOOL, SUB_WORKFLOW, CODE, SET_VARIABLE

每个节点类型对应唯一 ReactFlow `type`，并可从 `WorkflowSpecRegistry` 或 `/workflows/spec` 拉取参数规范做表单联想。

### 2.5 保存与校验

- **保存**：调用 `PUT /api/v1/workflows/{id}/config`，传递 `nodes`、`edges`，必要时包含 `variables`、`config`
- **保存前校验**：
  - 至少一个 START、一个 END
  - 无孤立节点（除 START 外均有入边）
  - 条件/分支节点出边数量符合规范
- **建议**：新增 `POST /api/v1/workflows/validate`，复用 `WorkflowValidator`，前端在保存前先校验

### 2.6 已知问题与修复建议

1. **WorkflowEditor**：`onNodesChange`/`onEdgesChange` 应使用 hook 返回的 `onNodesChange`/`onEdgesChange`，而非 `handleNodeChange`/`handleEdgeChange`（若后者未导出需修正引用）
2. **WorkflowAssembler.toConfig**：需实现将 `WorkflowConfigUpdateDto` 的 nodes/edges 正确写入 `WorkflowConfig`
3. **初始节点**：当前使用固定 5 节点模板，建议改为按类型从 palette 拖拽创建，或提供「从模板创建」选项

## 三、浏览器设计器完整功能设计

### 3.1 功能总览

| 分类 | 功能 | 优先级 | 参考 |
|------|------|--------|------|
| 画布 | 节点拖拽、连线、删除、撤销/重做 | P0 | 基础 |
| 画布 | 缩放、平移、小地图、网格/点阵背景 | P0 | ReactFlow |
| 画布 | 框选、多选、批量操作 | P1 | n8n |
| 节点 | 节点面板（按类型分类）、自定义节点 | P0 | n8n |
| 节点 | 节点配置面板（侧边栏/抽屉） | P0 | n8n |
| 节点 | 多 Handle 支持（CONDITION/SWITCH/PARALLEL） | P0 | 必须 |
| 执行 | 一键执行、输入变量表单 | P0 | 必须 |
| 执行 | 节点级/边级执行状态高亮 | P0 | n8n |
| 调试 | 断点/单步执行、Debug in Editor | P1 | n8n |
| 调试 | 历史执行加载到编辑器调试 | P1 | n8n |
| 执行 | 执行日志列表、筛选、重试 | P1 | n8n |
| 变量 | 全局变量管理、表达式联想 | P1 | n8n |
| 导入导出 | JSON/YAML 导入导出、版本对比 | P2 | n8n |
| 协作 | 实时协作（可选） | P3 | - |

### 3.2 调试功能设计（参考 n8n）

#### 3.2.1 执行模式

| 模式 | 说明 | API |
|------|------|-----|
| 同步执行 | 等待完成返回 `WorkflowExecuteResultVo` | `POST /execute` (mode= sync) |
| 异步执行 | 返回 executionId，轮询或 WebSocket 获取结果 | `POST /execute` (mode=async) |

#### 3.2.2 执行状态可视化

- 调用 `GET /executions/{executionId}` 获取 `ExecutionDetailVo`
- `nodeExecutions` 结构建议为：`{ [nodeId]: { status, outputs, error, startedAt, completedAt } }`
- 在前端：根据 `nodeExecutions` 为对应节点设置 `className`/`data-status`，展示：
  - 待执行：灰色/默认
  - 执行中：高亮/脉冲动画
  - 成功：绿色边框/勾
  - 失败：红色边框/错误图标

#### 3.2.3 Debug in Editor（n8n 特色）

- 从执行列表选择某次**失败执行**，点击「在编辑器中调试」
- 将历史执行的输入数据加载到当前画布，允许在不重新跑全流程的情况下：
  - 修改节点配置
  - 从该节点重新执行（需后端支持「从指定节点重跑」）
- 后端需支持：`POST /workflows/{id}/execute` 增加可选参数 `resumeFromNodeId`、`resumeInputs`

#### 3.2.4 断点/单步（进阶）

- 在节点上设置「断点」，执行到该节点时暂停，等待用户查看输入/输出后继续
- 需要：执行引擎支持暂停/恢复、前后端 WebSocket 或长轮询通信

#### 3.2.5 节点输入输出查看

- 执行完成后，点击节点展示：
  - 输入：上游节点输出合并后的变量
  - 输出：该节点的 `outputs`
- 建议在节点配置侧边栏增加「执行结果」 Tab，展示最近一次执行的输入/输出

### 3.3 执行日志与重试

| 功能 | 说明 |
|------|------|
| 执行列表 | `GET /execution-logs`，分页、按 workflowId/status 筛选 |
| 执行详情 | `GET /executions/{id}`，展示完整 nodeRecords、inputs、outputs、error |
| 重试 | 新增 `POST /executions/{id}/retry`，用原输入重新执行（或支持「用当前工作流版本重试」） |

### 3.4 变量与表达式

- 全局变量：在 `WorkflowConfig.variables` 中定义，支持 `${varName}` 引用
- 表达式：SpEL（后端）、可考虑前端提供简化表达式编辑器（如 `{{ $json.field }}` 风格）
- 节点配置表单：根据 `NodeTypeSpec` 的 `configParams` 生成表单，支持变量/表达式输入联想

### 3.5 多 Handle 与连接规则

| 节点类型 | 出边 Handle | 说明 |
|----------|-------------|------|
| CONDITION | `true` / `false` | 两条边，对应 ifTrue/ifFalse |
| SWITCH | `case_1`、`case_2`、`default` 等 | 多边，对应 cases 和 default |
| PARALLEL | `branch_1`、`branch_2`… | 多边，对应 branches |
| 其他 | 单 Handle | 单出边 → next |

ReactFlow 的 `sourceHandle`/`targetHandle` 需与上述语义一致，保存/转换时根据 handle 映射到 DSL。

### 3.6 导入/导出

- **导出**：将当前 `nodes`、`edges`、`variables` 等序列化为 JSON 或 YAML，可兼容 AgentX 的 `WorkflowDslParser` 格式
- **导入**：解析 JSON/YAML，转换为 ReactFlow 的 nodes/edges，并校验
- **版本对比**：保存历史版本，支持 diff 展示（可按节点/边粒度）

### 3.7 UI 布局建议

```
+------------------------------------------------------------------+
| [工作流名称] [状态] [未保存]     [保存] [执行] [调试] [全屏] [关闭] |
+------------------------------------------------------------------+
| 节点面板 |                   画布区域                    | 配置 |
| (分类)   |  [ReactFlow] 节点拖拽、连线、缩放...          | 面板 |
| START    |                                               | 选中 |
| END      |                                               | 节点 |
| LLM      |                                               | 的   |
| ...      |                                               | 配置 |
+------------------------------------------------------------------+
| 节点数: N  边数: M                    执行日志 | 变量 |
+------------------------------------------------------------------+
```
